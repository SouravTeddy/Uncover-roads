Phase 7 — Organic City Detection Design

How the app knows when pins are a new city vs more days in the same city

Detection flow — runs on every pin add
1

Pin added → geo-cluster check

New pin's lat/lon is compared against the centroid of all existing pins using haversineKm(). Already exists in codebase.

2

Distance threshold → classify

If new pin is within 80km of existing centroid → same city. If > 80km → potential new city. 80km covers large metro areas (Greater Tokyo, Greater London, etc.).

3

Reverse geocode → assign city name

If new city detected: reverse geocode the pin's coords to get city/admin name. Stamp _city on the place. Already uses Nominatim — same API, just reverse direction.

4

Transport mode → derive connection type

Run suggestTransportMode(distanceKm) on centroid-to-centroid distance. < 150km = train/bus, 150–600km = train/short-haul, > 600km = flight. Already exists.

5

UI moment → toast + footprint chip appears

Non-blocking toast slides up: "Looks like you're exploring Sydney ✈️ — it's a flight from Tokyo". FootprintChip for new city adds to bar. No modal, no interruption.

Dates in organic flow

User doesn't set dates upfront. When a new city is detected, the app shows a lightweight date prompt inside the toast: "When are you going? Add dates" — a small secondary action. Tapping opens a compact date range sheet for that city only. Dates remain optional — the engine works without them but shows a "Add dates for smarter planning" nudge on the Journey screen.
